## CRITICAL FINDING: SIGKILL CAPABILITY SURVIVAL
When loader receives SIGKILL (pkill -9), it cannot run cleanup:
- BPF object not closed → LSM programs remain attached
- Maps (tx_by_file, cap_epoch, etc.) persist in kernel
- New loader start loads SECOND set of programs + maps
- Pre-existing FD capabilities remain valid (tx_by_file entry intact)

This is a fundamental BPF LSM limitation: programs persist until
explicit detach or process cleanup. SIGKILL prevents both.

Mitigations for production:
1. systemd: `Restart=on-failure`, `KillSignal=SIGTERM`, `TimeoutStopSec=5`
2. Loader SIGTERM handler: graceful BPF detach + map cleanup
3. Startup: detect stale maps from previous crash, force cleanup
4. Capability epoch: RVKE on startup invalidates all stale caps

## ZERO ACTIVE BYPASSES
Every active attack vector tested was properly denied. The only
"bypass" is the passive survival of state across SIGKILL, which is
a deployment/ops concern, not a semantic enforcement gap.
